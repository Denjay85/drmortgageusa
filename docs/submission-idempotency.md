# Website submission retries

POST /api/quiz-submit uses the existing leads.event_id and saved payload as a durable receipt. Before looking up or inserting a lead, it acquires a transaction-scoped PostgreSQL advisory lock derived from that event ID. READ COMMITTED ensures the waiting request sees the previous transaction's committed row. Different IDs remain separate inquiries, including repeated inquiries from the same email. No schema migration, new credentials, backfill, or production replay is required.

A repeated ID and identical normalized payload return the existing lead ID and event ID with replayed: true. Conflicting details return 409 without changing the lead or exposing its receipt. The receipt's identity is reused; meta_capi on a replay reports the last persisted state, which may still be pending. Invalid IDs fail before database access. A lock wait exceeding five seconds returns 503 with Retry-After; retry the same body and ID.

The lead is committed before optional integrations. Only the request that inserts it attempts the initial Zapier/Meta dispatch. Failure before commit rolls back and permits a same-ID retry. A lost commit acknowledgment, worker exit after commit, webhook timeout, or delivery-status write failure must not trigger another dispatch through the public endpoint: a repeat returns the saved receipt. Existing queue fields and the authenticated manual retry endpoint remain unchanged. Never replay an uncertain queued result without reconciling the saved event ID against Zapier and Bonzo first. No historical leads are automatically replayed by this change.

There is no arbitrary TTL. Receipts persist with the existing lead records so a late request does not silently become a new inquiry. Existing retention/deletion practices remain applicable; deletion of a lead would also remove this receipt. No new personal-data store is introduced.

The React shared submission client keeps uncertain request bodies in page memory and reuses them for an unchanged inquiry. It clears the pending body after a confirmed receipt. Changed details or a new inquiry after success get a new ID. Nothing is added to browser storage. Reloading the page loses this memory; clients without an event ID continue receiving a generated ID for compatibility. The server guarantee concerns the same event ID, not blanket suppression of similar people or messages. Legacy clients must preserve their event IDs when retrying.

This provides one saved receipt and at most one initial dispatch attempt for a given event through this handler. It does not guarantee exactly-once delivery inside external systems, deduplicate arbitrary downstream webhook redelivery, or make an ambiguous external timeout safe to replay. The personal Zap's Never replay override remains in place. Manual queue replays and direct CRM operations remain explicit reconciliation decisions.

Validation uses real PostgreSQL 18 in an ephemeral CI service and a unique test schema. All Zapier and Meta calls are mocked. Cases include simultaneous repeats, replay while dispatch is in progress, distinct IDs, conflicting bodies, validation failures, rollback, lost commit acknowledgments, worker exit, webhook timeout and status-write failure. No production lead is used for duplicate testing.

Rollback: revert this change's application commit while retaining PR52 tracking and subsequent site work. No database rollback is required. Reverting removes this guard, so keep the personal workflow disabled if duplicate safety is again unresolved. Routing rollback is separate and must use the securely retained prior endpoint after reconciling in-flight deliveries.
